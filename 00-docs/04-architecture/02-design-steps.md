# Шаги проектирования

> Как из [драйверов](01-drivers.md) получается архитектура. Начинаем с самого простого решения
> и меняем его, только когда какой-то драйвер не выдерживает. Каждый шаг описан одинаково:
> какой драйвер нарушен → что меняем → чем за это платим.

## Шаг 0. Один сервис, одна база

```
          ┌───────────────────────────────────────┐
  все ──► │ один сервис: API, фон, переход,       │ ──► PostgreSQL
          │ статистика                            │
          └───────────────────────────────────────┘
```

Самое простое решение: один код, одна база, никаких сетевых вызовов. Проверяем его драйверами.

## Шаг 1. Переход — отдельный сервис

**Драйвер:** D-1, D-2 — переход за 20 мс, 99,99%, работает при отказе всего остального.

**Проблема.** Переход живёт в одном процессе с загрузкой файлов на 8 000 ссылок/с и записью кликов.
Пауза сборщика мусора, исчерпанный пул соединений или ошибка в коде загрузки — и переходы тормозят или падают.

**Решение.** Выносим переход в отдельный сервис **decode-service**. Всё остальное остаётся
в основном сервисе — **link-service**.

```
  создатель  ──► link-service ──┐
                                ├──► PostgreSQL
  посетитель ──► decode-service ┘
```

**Цена.** Второй сервис: отдельная выкатка, мониторинг, связь между сервисами.

## Шаг 2. У перехода своё хранилище

**Драйвер:** D-1, D-2.

**Проблема.** decode-service читает базу link-service:

- после сбоя кэша весь поток переходов уходит в базу, где создаются ссылки, и тормозит link-service;
- схема базы link-service становится общим контрактом: переименовал колонку — сломал переход.

**Решение.** У decode-service своё key-value хранилище **ScyllaDB** с кэшем **Redis** — «код → адрес».
Переходу нужен только поиск по ключу, реляционность ему не нужна.

```
  создатель  ──► link-service ──► PostgreSQL
                      │
                      │ синхронно при создании + события
                      ▼
  посетитель ──► decode-service ──► ScyllaDB + Redis
```

**Цена.** Появилась вторая копия ссылок, и её надо синхронизировать — так возникает драйвер **D-3**:
новая ссылка работает сразу, изменения доходят за 2 секунды. Поэтому:

- при создании link-service передаёт ссылку в decode-service **синхронно** и отвечает клиенту только после этого;
- все изменения дополнительно идут **событиями** через Kafka — это и обновления, и страховка,
  если синхронная передача не прошла.

## Шаг 3. Статистика — отдельный сервис

**Драйвер:** D-4 — до 30 000 записей кликов в секунду.

**Проблема.** Клики пишутся в ту же базу, где создаются ссылки. Это та же проблема, что на шаге 2, только на запись.

**Решение.** decode-service публикует событие о клике в Kafka и забывает о нём.
Отдельный **analytics-service** читает клики и пишет агрегаты по часам и дням в свою базу.

```
  посетитель ──► decode-service ──► клики ──► Kafka ──► analytics-service ──► PostgreSQL
```

**Цена.** Ещё один сервис. Отчёт статистики теперь требует двух сервисов: link-service проверяет владельца,
analytics-service отдаёт цифры. Это допустимо — доступность статистики 99,5%.

## Шаг 4. Фон отдельно от API

**Драйвер:** D-5 — файлы и проверки до 8 000 операций/с не тормозят API и не теряются.

**Проблема.** В link-service остались обработка файлов и проверки безопасности. В пике они забирают
CPU и соединения к базе у API — создание одной ссылки начинает тормозить.

**Решение.** Не новый сервис, а **две роли запуска** одного кода link-service:
`api` обрабатывает запросы, `worker` — фоновые задачи. Код, база и выкатка общие.
Фоновая задача хранится до подтверждения выполнения, поэтому падение worker её не теряет.

**Цена.** Нужно следить, какие компоненты активны в какой роли. Зато не появляется копии данных —
файлы и проверки работают с теми же ссылками.

## Шаг 5. Вход — отдельный auth-service

**Драйвер:** D-7 — вход и учётные данные: security-критичный код и дорогая по CPU проверка пароля.

**Проблема.** Регистрация, пароли, подтверждение email, сброс пароля, токены, API-ключи живут в link-service:

- хэши паролей и ключей лежат в одной базе со ссылками — уязвимость в коде ссылок открывает и их;
- проверка пароля намеренно медленная: BCrypt тратит ~100 мс CPU на одну попытку.
  Атака перебором паролей съедает CPU link-service, и начинает тормозить создание ссылок.

**Решение.** Выносим всё про учётные данные в отдельный **auth-service** на Spring Security:

- регистрация, подтверждение email, вход, выход, смена и сброс пароля (F-1);
- API-ключи для программ (F-2) — это тоже учётные данные;
- выпуск токенов: короткий **access-токен** (JWT, 15 минут) и **refresh-токен**, который хранится в базе
  и отзывается при выходе (F-1.9);
- публичный ключ для проверки подписи токенов (JWKS).

Остальные сервисы проверяют подпись токена сами — ключом, скачанным у auth-service один раз.
Всё, что им нужно, — `accountId` и `emailVerified` — лежит в самом токене, поэтому в auth-service
во время запроса никто не ходит.

```
  создатель ──► auth-service ──► PostgreSQL (аккаунты, ключи)
                    │
                    │ access-токен
                    ▼
  создатель ──(токен)──► link-service    подпись проверяется локально
```

**Почему не готовое решение.** Keycloak закрыл бы большую часть F-1 без кода. Но цель проекта — научиться,
поэтому пишем сами. Риск снижаем стандартными средствами Spring Security и тестами — своей криптографии не пишем.

**Цена.** Ещё один сервис и свой security-код, который нужно тщательно покрыть тестами.

## Шаг 6. Хранилище статистики

**Драйвер:** D-4.

**Проблема.** ~45 ГБ сырых кликов в день. Для такого объёма обычно берут колоночную базу — ClickHouse.
Но предел Postgres на наших агрегатах ещё не измерен.

**Решение.** Начинаем с агрегатов по часам и дням в Postgres. На ClickHouse переходим,
когда нагрузочный тест покажет, что Postgres не держит запись на пике
или отчёты не укладываются в 500 мс.

**Цена.** Возможно, придётся переезжать.

## Итог

| Шаг | Драйвер        | Решение                                     |
|-----|----------------|---------------------------------------------|
| 1   | D-1, D-2       | Переход — отдельный сервис decode-service   |
| 2   | D-1, D-2 → D-3 | Своё хранилище у decode-service             |
| 3   | D-4            | Статистика — отдельный analytics-service    |
| 4   | D-5            | Роли api и worker у link-service            |
| 5   | D-7            | Вход и ключи — отдельный auth-service       |
| 6   | D-4            | Postgres сейчас, ClickHouse по замеру       |
| —   | D-6            | Ссылки, файлы, проверки — один link-service |
